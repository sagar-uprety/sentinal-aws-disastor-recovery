# Code Explainer Progress - Pilotlight (aws-pilotlight-multi-region-dr)

## Overview
Multi-region AWS disaster recovery project, pilot-light strategy. Two independent systems: a PostgreSQL-backed URL-shortener workload (active in one region, pilot-light standby in a second, compute scaled to 0 in secondary until failover) and a monitoring service that lives in its own region/account-level failure domain so it survives a full workload-region failover. Terraform for infra, Go for the workload and sentry services.

- [x] scripts/drills/failback.sh - walked block-by-block + refactored 2026-08-23. REAL BUG FOUND on the block-by-block pass: wait_for_replica_lag returns the FIRST datapoint satisfying lag<=target, and the post-freeze cutover gate was using the same loose 300s FAILBACK_LAG_TARGET_SECONDS as the pre-freeze/post-reset checks - so a 250s reading would be accepted and promote-read-replica would permanently lose up to 250s of secondary writes. step_ready's link check does NOT catch this (that slug predates the outage and is long-replicated; the at-risk writes are the ones made while secondary was serving). Whole point of freezing writes first is to let replication drain to 0. Fixed: added FAILBACK_CUTOVER_LAG_SECONDS (default 0) + wait_for_replica_lag now takes an optional per-call target, defaulting to the general 300s. Escape hatch documented in the runbook since this gate fires while the app is deliberately offline. Also checked and DISMISSED two of my own earlier suspicions: primary_promoted is NOT dead (it's in the real drill-events.log as a phase-boundary timestamp - evidence for humans, not code; dedup guard prevents conflicting timestamps on resume), and the double wait_for_replica_lag is justified (pre-freeze gate runs while the app is still serving, so it catches lagging replication BEFORE downtime starts; 10min is a ceiling, both normally exit on the first poll). Was 7 separately-invoked subcommands (8 manual CLI calls total across the failback). User pushed back on the granularity; researched it - AWS's own DR Orchestrator Framework (Prescriptive Guidance) runs the whole failback sequence as ONE Step Functions execution with a single human go/no-go, and REL13-BP05 says "convert manual runbooks into code" with gates on decisions-that-matter, not every mechanical check. Found nothing recommending per-step manual gates. Refactored: each step body extracted into a step_* function, added `cutover` (verify-replica -> freeze-writes -> promote-primary -> ready, one CONFIRM_FAILBACK_CUTOVER=YES) and `finalize` (verify-reset -> delete-snapshot, derives snapshot id from the recorded drill event). Single steps all still callable for resuming a failed chain. switch-traffic.sh primary deliberately left separate per user. 2 CI dispatches unchanged. Every original check/guard/exit preserved byte-for-byte inside the functions. All 7 drill scripts pass shellcheck -x clean. runbook-failover.md steps 3/5 updated.
